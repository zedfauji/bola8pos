<threat_model>
Scope note: narrow by design. The question is whether adding one client-supplied parameter to an existing server-side RPC call can bypass or weaken the already-shipped `STALE_VERSION` guard.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → edge function | Untrusted JSON body over `fetch`, authenticated by user JWT; validated by `BodySchema` before any use. |
| edge function → Postgres | Service-role client (`admin`) — full privilege. Every value forwarded to the RPC crosses this boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-05 | Tampering | `expectedVersion` forwarded to a service-role RPC call | high | mitigate | The field is validated by `BodySchema` (`z.number().int().nonnegative()`) *before* it reaches `admin.rpc`, so only a non-negative integer can be forwarded. It is a named RPC parameter, never string-interpolated into SQL, so no injection surface is created. `process_payment_atomic` is `SECURITY DEFINER` and compares the value against the locked row under `FOR UPDATE` — a forged value can only cause the caller's own payment to be rejected, never another row to be written. |
| T-15-06 | Tampering | omitting `expectedVersion` to bypass the guard | medium | accept | A malicious client can always omit the field and get today's unguarded behavior. This is unchanged from the current shipped state and is the documented null-tolerant contract in D-02. Optimistic concurrency is a correctness control against concurrent honest terminals, not an authorization control; authorization stays with RLS and the RPC's own tab-state checks. Making the field required would break `useSplitTab` and the rappi-order store, which have no tab version in scope. |
| T-15-07 | Denial of service | forged low `expectedVersion` causing repeated payment rejection | low | accept | Self-inflicted only — a client can already refuse to pay. The RPC rejects and returns an error envelope; no row is written, no lock is held past the transaction. |
| T-15-08 | Information disclosure | `expectedVersion` in edge-function request logging | low | mitigate | `expectedVersion` is a monotonic row counter carrying no PII or secret. Do not add it to any log line that also carries `terminalReference` or `referenceNumber`, both of which are already marked never-log in `edge-function-contracts.ts`. |

No package-manager installs in this plan — supply-chain threat `T-15-SC` does not apply.

No `supabase/migrations/*.sql` files are touched. `supabase/functions/process-payment/index.ts` is an edge function, not a migration, so no `npx supabase db push` task is required. Deploying the edge function is covered by the plan 15-09 checkpoint, since the E2E run exercises it.
</threat_model>
