<objective>
Close carry-forward gap 1 from `VERIFICATION.md` (expanded per D-01): make Group-B client-side optimistic-concurrency conflicts actually *observable*, then wire `handleVersionError` into every Group-B call site that lacks it.

Purpose: today the `.eq('version', expected)` guards in these hooks are inert. PostgREST returns no error and no body for an UPDATE that matches zero rows, and `supabaseMutation` maps that to `ok(null)` — so a stale write silently no-ops and the user sees a success toast. Wiring `handleVersionError` alone would be dead code because the error it handles can never materialize. Both halves ship together.

Output: `versionedMutation` helper + `TERMINAL_ID` export in `shared/lib`, and four Group-B call sites emitting the standard conflict UX.
</objective>

<threat_model>
Scope note: this plan wires an existing, already-reviewed conflict-handling path into additional call sites. The threat model is scoped to whether those new call sites can *bypass* the existing `STALE_VERSION` guard — not a re-review of the Phase 15 concurrency design (schema, triggers, and RPC guards are out of scope and untouched).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → PostgREST | Authenticated staff JWT; RLS enforces row access. The `.eq('version', …)` filter is a client-supplied predicate and is NOT a security control. |
| renderer → `record_audit` RPC | Fire-and-forget audit write carrying `terminal_id` and `expected_version`, both client-supplied. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-01 | Tampering | `versionedMutation` zero-row branch | medium | mitigate | The client-side guard is defence-in-depth only. Authoritative enforcement stays in the `bump_version_on_update` trigger (rejects any UPDATE not advancing version by exactly +1) — already shipped and untouched. A caller that omits `.select(...)` degrades to the current silent-no-op behavior, never to a last-write-wins overwrite, because the trigger still rejects a non-advancing UPDATE. |
| T-15-02 | Spoofing | `handleVersionError` `terminalId` / `expectedVersion` audit payload | low | accept | Both fields are client-supplied and land in `p_before` of an audit row. They are diagnostic breadcrumbs, not authorization inputs; `record_audit` records the authenticated actor server-side. Accepting a spoofable diagnostic field matches the already-shipped behavior at the four existing call sites. |
| T-15-03 | Information disclosure | `.select('id')` appended to version-guarded UPDATEs | low | mitigate | Only the primary key of a row the caller just updated is returned, and RLS applies to the returned representation identically to any other SELECT. No new column is exposed. |
| T-15-04 | Elevation of privilege | new `versionedMutation` call sites | low | accept | The helper adds no privilege: it wraps `supabaseMutation`, which uses the same anon-key + user-JWT client as before. No service-role key is introduced into the renderer. |

No package-manager installs in this plan — the supply-chain threat `T-15-SC` does not apply (no new npm/pip/cargo dependency).

No `supabase/migrations/*.sql` files are touched — no schema push task is required.
</threat_model>
