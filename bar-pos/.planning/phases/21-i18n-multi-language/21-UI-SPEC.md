# Phase 21 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Phase Nature (read first)

This is **not** a new-screens phase. It is a technical migration (react-i18next wiring + big-bang string extraction, per CONTEXT.md D-04). The hard visual contract for the migration itself is: **zero visual regression** — every existing component, layout, spacing, color, and copy *content* stays pixel-identical; only the *source* of each string changes (hardcoded literal → `t('key')` catalog lookup). This is enforced by re-running the existing Phase 34 visual baseline (`e2e/visual/45-visual-baseline.spec.ts`) post-migration, not by this document.

Two genuinely new UI surfaces exist in this phase, both narrow and both use existing shared/ui components only — no new visual design, no new components:

1. **Self-service language switcher** — a new, role-agnostic "Language" tab in `SettingsTabsPanel`, per the coordinator's locked decision below.
2. **Admin per-staff locale field** — a new editable field on the Staff management page (`/staff`, `StaffDashboard`), gated `manage_staff`, per D-03.

### Locked decision (coordinator override, this session)

**Bartenders are included in self-service locale switching.** `SettingsTabsPanel` gets a third, role-agnostic tab group that renders for every authenticated role, independent of `can('manage_settings')`/`can('manage_products')`. This resolves RESEARCH.md's Pitfall 1 / Open Question 2. The admin-editable locale-per-staff field on the Staff page (D-03) ships in addition to this, not instead of it — two separate write paths to `profiles.locale`:

| Path | Who | Where | Gate |
|------|-----|-------|------|
| Self-service | Any authenticated staff member (incl. bartender) | Settings → Language tab | none — always visible once logged in |
| Admin override | Manager/admin setting another staff member's locale | Staff page (`/staff`) | `manage_staff` (existing RBAC action) |

## Typography

**No new typography scale.** Reuses sizes already present in `SettingsTabsPanel` tabs. Weight is capped at 2 (Dimension 4): 400 regular for body/caption text, 500 medium for anything emphasized (labels and the section heading alike — differentiated from body by size/line-height, not weight). This is a deliberate collapse from `GeneralSettingsTab.tsx`'s literal `font-semibold` (600) h2 — the new Language-tab heading uses `font-medium` instead, since it's new markup, not a byte-for-byte clone of existing migrated copy (the zero-visual-regression contract applies to migrated strings, not to this phase's two brand-new elements).

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-----------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 | Form labels' input text, table cells, helper text |
| Label / Heading | 14px (`text-sm`) label, 18px (`text-lg`) heading | 500 (medium) | 1.5 (label) / 1.2 (heading) | Form field `<Label>` (shadcn default, matches existing usage everywhere) and the new "Language" section heading (`text-lg font-medium`, not `font-semibold`) |

## Copywriting Contract

Every string below ships as an i18next key from day one (per D-04/D-05 — no hardcoded literal is acceptable, including in this contract's own implementation). Keys shown are suggested `settings`/`staff` namespace paths; planner may rename to match the chosen namespace scheme in RESEARCH.md.

| Element | es-MX (default) | en-US | Key |
|---------|------------------|-------|-----|
| Settings tab label | Idioma | Language | `settings.tabs.language` |
| Section heading | Idioma | Language | `settings.language.heading` |
| Field label | Idioma de la interfaz | Interface language | `settings.language.fieldLabel` |
| Select option — es-MX | Español (México) | Español (México) | `settings.language.option.esMX` |
| Select option — en-US | Inglés (EE. UU.) | English (US) | `settings.language.option.enUS` |
| Helper text | Aplica solo a tu cuenta y persiste entre dispositivos. | Applies only to your account and persists across devices. | `settings.language.helper` |
| Primary CTA (Save) | Guardar idioma | Save Language | `settings.language.save` |
| Save — pending label | Guardando… | Saving… | `settings.language.saving` |
| Save success toast | Idioma actualizado. | Language updated. | `settings.language.saveSuccess` |
| Save error toast | No se pudo actualizar el idioma. Intenta de nuevo. | Couldn't update language. Try again. | `settings.language.saveError` |
| Staff table column header | Idioma | Language | `staff.table.locale` |
| Staff-page inline edit (admin) — trigger | Cambiar idioma | Change language | `staff.locale.editTrigger` |
| Staff-page inline edit — success toast | Idioma de {name} actualizado a {locale}. | {name}'s language updated to {locale}. | `staff.locale.updateSuccess` |
| Staff-page inline edit — error toast | No se pudo actualizar el idioma de {name}. | Couldn't update {name}'s language. | `staff.locale.updateError` |

No empty state applies (a locale value always exists — D-02 defaults every profile to `es-MX`, `LocaleSchema.default('es-MX')` per RESEARCH.md). No destructive action exists in this phase's new UI — switching a locale is instantly reversible and needs no confirmation dialog (do not add one).

Generic error-state pattern for both surfaces (reuse existing `toast.error(result.error.message)` convention already used identically in `GeneralSettingsTab.tsx`/`EditRoleDialog.tsx`): show the mutation's `Result.error.message` via `toast.error()`, fall back to the table row above if the write fails — no separate error screen.

## Interaction Contract — Settings → Language tab

Mirrors `GeneralSettingsTab.tsx` exactly (same dirty-tracking pattern, same button state machine):

1. Tab renders with the current staff's locale pre-selected in a `Select` (`es-MX` | `en-US`, sourced from `LocaleSchema.options`, same enum-driven pattern as `EditRoleDialog.tsx`'s role `Select`).
2. Selecting a different option marks the form dirty (`setDirty(true)`) but does **not** immediately call `i18n.changeLanguage()` — the UI-language switch and the persisted-preference write happen together on Save, avoiding a half-saved state if the mutation fails.
3. `POSButton` (`touchSize="large"`, primary variant) is disabled until dirty; label switches to the "Saving…" copy while `mutation.isPending`.
4. On success: `i18n.changeLanguage(locale)` fires, `toast.success(...)`, `setDirty(false)`. The whole app's visible strings switch language immediately (no reload required) because `i18next` reactively re-renders subscribed components.
5. On failure: `toast.error(...)`, form stays dirty/editable, selection is not reverted (user can retry Save without re-selecting).

## Interaction Contract — Staff page admin field

Reuses the existing `StaffDashboard` `DataTable` column pattern (see `StaffDashboard.tsx` Role column) plus the existing `EditRoleDialog`-style `Select` inside a small edit affordance — **do not build a new dialog component**; extend `EditRoleDialog`'s pattern or add a sibling `EditLocaleDialog` that is a near-identical copy (same Dialog/DialogContent/Select/Button structure, swapping role→locale), gated the same way (`ProtectedAction action="manage_staff"`, matching the existing "Force PIN Change" row-action gate already on this table).

1. New `DataTable` column "Language" shows the staff member's current locale as a `Badge variant="outline"` (matching the existing Role column's badge styling exactly — same size, same variant, just different text content: "es-MX" / "en-US").
2. A per-row action button ("Change language") opens the locale-edit dialog, gated `manage_staff` — same `ProtectedAction` wrapper already used for "Force PIN Change" in this exact table.
3. Dialog: single `Select` (locale options), Cancel/Save footer — identical footer button structure to `EditRoleDialog.tsx` (`variant="outline"` Cancel, primary Save, `disabled` while pending).
4. Does **not** call `i18n.changeLanguage()` on the acting admin's own session — this write only affects the target staff member's stored `profiles.locale`; their own UI language changes on their next login/session hydrate (per RESEARCH.md Pattern 2 — locale is read on staff-store hydrate, not pushed live to another logged-in session).
