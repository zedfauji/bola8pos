<root_cause_brief>
Verified directly against the live migration, not taken on trust from 20-PATTERNS.md.

`supabase/migrations/20260710000001_promotions_schema.sql` lines 19, 26-27 define
three relevant constraints on `promotions`:

- the `target_type` enum CHECK admits exactly `item`, `category`, `pool_billing`,
  `pool_grant`;
- `promotions_item_target_check` requires `target_product_id IS NOT NULL` whenever
  `target_type = 'item'`;
- `promotions_category_target_check` requires `target_category_id IS NOT NULL`
  whenever `target_type = 'category'`.

`pool_billing` and `pool_grant` have no companion NOT-NULL requirement — they are
the two target types that legitimately carry no FK. `pool_billing` is therefore a
valid neutral default for an incomplete draft row.

Two client call sites can emit a payload that violates those constraints:

1. `src/entities/promotion/model/queries.ts` line 102 — the draft insert hardcodes
   the `item` target type with no product FK. This is the reported G-20-2 failure.
2. `src/features/manage-promotions/ui/PromotionBuilderForm.tsx` `handleSave`
   (lines 118-162) — validates name, discount value and priority, but never
   validates that an item target has a product or a category target has a
   category. Line 147 coerces an unselected product to null and sends it, which
   reproduces the identical 23514 through `useMutationUpdatePromotion`. The UAT
   never reached this path because creation failed first; the natural post-fix
   flow (create draft → switch Applies-to to Item → forget the product → Save)
   hits the same cryptic toast the user reported. Task 2 closes it.

Neither Zod schema guards target consistency — `PromotionSchema` /
`PromotionUpdateSchema` (src/shared/lib/domain.ts lines 2098-2116) refine only the
percentage bound — and `useMutationUpdatePromotion` does not parse its input at
runtime, so a schema-level refine would not fire. The guard belongs in the one
place that assembles a complete target payload: `handleSave`.

Rejected alternative (documented, not chosen): relaxing
`promotions_item_target_check` via a new migration to permit FK-less drafts while
`is_active = false`. That preserves Item as the visible default but weakens a
correct constraint and requires a schema push. The client-side neutral default is
smaller, weakens nothing, and matches what this phase's own integration tests
already do (`promotions-schema.integration.test.ts` seeds `pool_billing` rows
precisely because they need no FK). No migration is required by this plan, so the
schema push gate does not apply.
</root_cause_brief>
