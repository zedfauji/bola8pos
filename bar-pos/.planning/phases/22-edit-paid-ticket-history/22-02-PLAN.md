Body in this order:
    1. Role re-check: `SELECT id INTO v_staff_id FROM profiles WHERE id = auth.uid() AND role IN ('manager','admin')`; `IF NOT FOUND THEN RAISE EXCEPTION 'AUTH_FORBIDDEN: manager or admin role required'` (mitigates T-22-02; copy from process_refund).
    2. Version guard: `SELECT version, status INTO v_current, v_status FROM tabs WHERE id = p_tab_id FOR UPDATE`; if version is NULL raise `NOT_FOUND_VERSIONED` USING ERRCODE='P0V02'; if `p_expected_version IS NOT NULL AND v_current <> p_expected_version` raise `STALE_VERSION` USING ERRCODE='P0V01'; if `v_status NOT IN ('paid','closed')` return `jsonb_build_object('ok', false, 'code', 'TAB_NOT_EDITABLE', ...)` (only paid/closed tabs are correctable — this is a correction tool, not a reopen; Phase 23 out of scope).
    3. Capture `v_before := to_jsonb(t.*) || jsonb_build_object('items', (SELECT jsonb_agg(to_jsonb(oi.*)) FROM order_items oi JOIN orders o ON o.id=oi.order_id WHERE o.tab_id=p_tab_id AND oi.is_deleted=false))` from the tab row `t`.
    4. Compute `v_old_total` as the item subtotal BEFORE the patch using the SAME basis process_payment_atomic uses: `SUM(oi.unit_price * oi.quantity) WHERE oi.parent_order_item_id IS NULL AND oi.is_deleted=false` over the tab's orders (Pitfall 3 — never compare against payments.amount).
    5. Apply the WHITELISTED patch by iterating `jsonb_array_elements(p_order_item_patches)` where each element has an `op` discriminator: `op='update'` → `UPDATE order_items SET quantity=COALESCE((e->>'quantity')::int, quantity), unit_price=COALESCE((e->>'unit_price')::numeric, unit_price), notes=COALESCE(e->>'notes', notes), updated_at=NOW() WHERE id=(e->>'id')::uuid AND order_id IN (tab's orders)`; `op='delete'` → soft-delete `UPDATE order_items SET is_deleted=true, deleted_at=NOW() WHERE id=(e->>'id')::uuid AND order_id IN (tab's orders)`; `op='add'` → `INSERT INTO order_items (order_id, product_id, quantity, unit_price, notes)` picking the tab's most-recent order id. Destructure ONLY the named keys id/op/quantity/unit_price/notes/product_id — never build a dynamic column-name UPDATE (mitigates T-22-01). This is D-01's whitelist: `order_items.quantity`, `order_items.unit_price`, `order_items.notes`, add/soft-delete rows, and `tabs.notes`. Do NOT touch `payments` (Anti-Pattern in RESEARCH.md) and do NOT add or write any discount column — a lowered `unit_price` IS the discount mechanism (Pitfall 2). Do NOT call `deplete_for_order_item` / any inventory function — Open Question 1 resolved: inventory is NOT touched by this pure billing correction.
    6. Apply `tabs.notes = COALESCE(p_notes, notes)`.
    7. Compute `v_new_total` on the SAME basis as step 4, after the patch. Set `v_delta := v_new_total - v_old_total`.
    8. Offsetting caja entry (D-02 / D-03 / Open Question 2 resolved): `IF v_delta <> 0 THEN SELECT id INTO v_caja FROM caja_sessions WHERE status='open' LIMIT 1; IF NOT FOUND THEN RAISE EXCEPTION 'NO_OPEN_CAJA: an open caja session is required to record a total-changing edit'; END IF; INSERT INTO caja_entries (caja_session_id, type, amount, concept, staff_id) VALUES (v_caja, CASE WHEN v_delta>0 THEN 'income' ELSE 'expense' END, abs(v_delta), <concept>, v_staff_id); END IF`. Build `<concept>` as a structured-then-reason text that fits the 1..200 char CHECK: prefix with the tab short id and its original date, then a sanitized `p_reason` — strip characters that would break later text parsing (comma/period/parenthesis, mirroring `sanitizeSearch`) and truncate the whole concept to 200 chars (mitigates T-22-04). Add an SQL comment noting this free-text encoding is deliberate and that Phase 23 may later add `caja_entries.source_tab_id`/`source_type` columns to replace it (Open Question 3 resolved: do NOT add those columns now). Notes-only edits (`v_delta = 0`) skip this block entirely and proceed regardless of caja state.
    9. Bump version: `UPDATE tabs SET version = version + 1, updated_at = NOW() WHERE id = p_tab_id` (copy verbatim from create_order_with_items — the bump_version_on_update trigger enforces exact +1; mitigates T-22-03 even though tabs fields barely change).
    10. Build `v_after := to_jsonb(t2.*) || jsonb_build_object('items', <re-aggregated live items>) || jsonb_build_object('reason', p_reason)` (reason embedded as a synthetic key, mirroring the `_truncated` precedent — no new reason column, per RESEARCH.md Summary).
    11. `PERFORM record_audit('tab.edit_paid', 'tab', p_tab_id, v_before, v_after, 'rpc')` on the SUCCESS path only (never inside EXCEPTION — a raised exception rolls back the audit insert; Pitfall 1 ordering).
    12. `RETURN jsonb_build_object('ok', true, 'newTotal', v_new_total, 'delta', v_delta, 'cajaAdjustmentRecorded', v_delta <> 0)`.
    EXCEPTION block: `WHEN sqlstate 'P0V01' THEN RAISE;` `WHEN sqlstate 'P0V02' THEN RAISE;` `WHEN OTHERS THEN RETURN jsonb_build_object('ok', false, 'code', 'INTERNAL', ...)` — re-raise the version SQLSTATEs so PostgREST propagates them (do not swallow). `GRANT EXECUTE ON FUNCTION public.edit_paid_tab(uuid, int, jsonb, text, text) TO authenticated`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → edit_paid_tab RPC (payload) | Untrusted `p_order_item_patches` jsonb crosses here — could carry extra/unexpected keys |
| client → edit_paid_tab RPC (identity) | Any authenticated client can call the RPC directly, bypassing the UI PIN dialog |
| concurrent editors → tabs row | Two managers may patch the same paid tab simultaneously |
| p_reason → caja_entries.concept | Free-text reason is concatenated into a structured concept string |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-01 | Tampering | edit_paid_tab patch payload | high | mitigate | Named jsonb keys only (id/op/quantity/unit_price/notes/product_id), explicitly destructured; no dynamic column-name SQL; `payments` never touched |
| T-22-02 | Elevation of Privilege | edit_paid_tab called directly by non-manager | high | mitigate | Server-side `SELECT id FROM profiles WHERE id=auth.uid() AND role IN ('manager','admin')` → `AUTH_FORBIDDEN` (copied from process_refund); PIN dialog is UX-only |
| T-22-03 | Tampering (data race) | concurrent edits to same paid tab | medium | mitigate | `p_expected_version` + `FOR UPDATE` lock + `bump_version_on_update` trigger (Phase 15 Group A); P0V01 re-raised, not swallowed |
| T-22-04 | Tampering (injection) | p_reason → caja_entries.concept encoding | low | mitigate | Strip `,.()` from reason and truncate concept to the 200-char CHECK before concatenation (mirrors sanitizeSearch) |
| T-22-SC | Tampering | npm/pip/cargo installs | high | accept | Zero new packages this phase (RESEARCH.md Package Legitimacy Audit N/A); no install task, no checkpoint required |
