<objective>
Confirm the concrete schema shape that implements D-01 (loose piece is a distinct catalog product linked to its parent package product) and D-07 (strictly one active open unit per product) before any migration is authored or pushed.

Purpose: D-01 and D-07 are rated **costly** in 27-CONTEXT.md, but the *specific artifact* that carries them — the `open_units` table columns plus two new `products` columns, and the partial unique index — becomes a one-way door the moment `supabase db push` applies it to the remote Supabase Cloud project. This project has no automated migration rollback (CLAUDE.md: "Supabase Cloud has no automated rollback mechanism"), so renaming a column or reversing the FK direction afterwards costs a real corrective migration plus a coordinated client change across 6 downstream plans. 27-RESEARCH.md flags exactly this in its Assumptions Log: A2 (does `open_units.product_id` reference the BOX product or the LOOSE product?) and A3 (exact column names) are *synthesis, not verified fact*, and 27-CONTEXT.md's Claude's-Discretion block explicitly leaves the linkage direction unsettled.

This plan contains no implementation. It exists solely to walk the human through the door before the agent does.

Output: A resolved `checkpoint:decision` recorded in 27-01-SUMMARY.md, naming the exact table name, column names, status values, and linkage direction that plan 27-02 will implement verbatim.
</objective>

  <context>
D-01 locks the *model* (loose piece = distinct product linked to a parent package product) and D-07 locks the *invariant* (one active open unit per product), but neither fixes the physical schema. 27-RESEARCH.md's recommended shape is an assumption (A2/A3), and 27-CONTEXT.md's Claude's-Discretion block hands the linkage direction and column naming to the implementer. Because Supabase Cloud has no automated rollback in this project, the first `supabase db push` (plan 27-02, Task 2) is the point of no cheap return: after it, `open_units.remaining_count` is read by 4 RPCs, 1 Zod schema, 4 TanStack Query hooks, 3 features, and 1 widget.

Recommended option (A) is what 27-RESEARCH.md, 27-PATTERNS.md, and this codebase's `caja_sessions` precedent all point at. Options B and C are listed because they are the two shapes a reader might reasonably expect instead, and because picking either one *after* the push is the expensive scenario this gate exists to prevent.
  </context>
  <options>
    <option id="option-a">
      <name>A (recommended) — open_units.product_id references the BOX product; link lives on products.parent_product_id</name>
      <pros>Matches 27-RESEARCH.md A2 and the `caja_sessions` analog exactly. Makes D-07's invariant a literal one-line partial unique index (`ON open_units (product_id) WHERE status = 'active'`) with no extra join. Keeps `consume_open_unit`'s lookup a single `SELECT parent_product_id FROM products WHERE id = <loose id>`. Reuses the existing `products` `select('*')` query so the product grid needs no query change (D-01's "shown like any other product"). Shape: `open_units(id, product_id -> products.id [BOX], remaining_count int CHECK >= 0, status text CHECK IN ('active','exhausted','void'), opened_by, opened_at, closed_by, closed_at, closed_reason, created_at, updated_at)`; `products.units_per_package int NULL` (set on BOX, D-02); `products.parent_product_id uuid NULL REFERENCES products(id)` (set on LOOSE, D-01).</pros>
      <cons>Two nullable columns added to the hot `products` table. `remaining_count` names a different unit (pieces) than sibling `inventory.quantity_on_hand` (packages), which a future reader must not conflate.</cons>
    </option>
    <option id="option-b">
      <name>B — open_units.product_id references the LOOSE product instead</name>
      <pros>The consuming RPC needs no parent lookup at all — the sale's product id is the row's key directly.</pros>
      <cons>Breaks D-07's own framing ("one active open unit per *product*" naturally means one open box per box product). Two different loose products sharing one package product could each hold an active unit for the same physical box. The partial unique index would then enforce the wrong invariant, and undoing that after the push means rewriting the index, the RPC targeting logic, and backfilling every existing row.</cons>
    </option>
    <option id="option-c">
      <name>C — no products.parent_product_id; put the loose-product link on open_units instead (e.g. open_units.loose_product_id)</name>
      <pros>Leaves the `products` table untouched apart from `units_per_package`.</pros>
      <cons>The order-entry hot path (`deplete_for_order_item`) would have to query `open_units` to discover whether the product being sold is a loose piece at all — a table that may legitimately have zero rows for that product, so "is this a loose-piece product?" becomes unanswerable when nothing is open. That forces a second lookup table or a nullable flag anyway. 27-RESEARCH.md rejects this on "keeps `consume_open_unit` and the product-grid query simplest" grounds.</cons>
    </option>
  </options>
