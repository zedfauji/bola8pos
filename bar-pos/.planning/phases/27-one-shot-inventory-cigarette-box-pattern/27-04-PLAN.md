<objective>
Add the three manual lifecycle RPCs the admin Open-Units tab drives — `open_open_unit` (bartender+, D-11), `correct_open_unit` and `void_open_unit` (manager+, D-12) — and prove their RBAC guards, the D-08 rejection path, and their audit wiring against the live remote schema.

Purpose: `consume_open_unit` (plan 27-02) auto-opens units as a side effect of selling, which is enough for the sale path but not for SC-3 ("lets staff manually open a new one") or D-10 (correct the count / void a unit early). These three functions are the write API the UI layer in plans 27-07 and 27-08 calls; authoring and testing them before any React code exists means the UI has a proven contract to bind to instead of a moving target.

The RBAC split is the security-relevant part. D-11 puts opening a unit at bartender+ because it is a high-frequency, low-risk action at a busy bar; D-12 puts count correction and early void at manager+ because both are stock write-off vectors. The client-side `ManagerPinDialog` is UX; the `get_user_role()` guard inside each function body is the actual control (the `process_refund` precedent), which is why the tests here call the RPCs directly as a bartender rather than through any UI.

Runs in the same wave as plan 27-03: both depend only on 27-02's pushed schema and they share no files (this plan owns a new migration and a distinct `open-unit-lifecycle.integration.test.ts`).

Output: 1 applied migration with 3 RPCs, and a green integration test covering RBAC, the unique-violation path, and audit wiring.
</objective>

One migration containing three functions, following the repo's `-- UP:` / `BEGIN; ... COMMIT;` / trailing `-- DOWN:` comment-block convention.

**`open_open_unit(p_product_id uuid) RETURNS uuid`** — bartender+ per D-11. Guard: `IF get_user_role() IS NULL OR get_user_role() = 'kitchen' THEN RAISE EXCEPTION 'AUTH_FORBIDDEN: bartender or higher required to open a unit'; END IF;` (the same shape `deplete_for_order_item` uses — bartender+ is the floor, so no new `StaffAction` is minted). Then:
  - Read the product's `units_per_package INTO v_per_package`; if NULL raise `VALIDATION_ERROR: product % is not configured for open units` — D-04's genericity means this configuration check is the only thing that makes a product openable.
  - Lock the product's `inventory` row (`SELECT quantity_on_hand ... FOR UPDATE`). If no row or `quantity_on_hand < 1`, raise `INVENTORY_NEGATIVE: no unopened package available for product %`. This function's signature deliberately exposes no negative-stock bypass parameter of any kind — D-05 scopes the override to the order-entry path where a manager PIN gate already exists, and a bypass here would be the "second override mechanism" D-05 explicitly rejects. Its parameter list is exactly `(p_product_id uuid)`.
  - `INSERT INTO open_units (product_id, remaining_count, status, opened_by)` with `v_per_package`, `'active'`, and `auth.uid()`, wrapped in `BEGIN ... EXCEPTION WHEN unique_violation THEN ... END` — do NOT pre-check for an existing active row. On the `unique_violation`, read the existing active row's `remaining_count` and raise `DUPLICATE_ENTRY: an open unit already exists for this product (% remaining) — sell through it first`, which is D-08's required wording with the live count interpolated. Catching the index violation rather than looking first is also what makes two bartenders tapping simultaneously safe: the loser gets the friendly message instead of creating a second active row.
  - Decrement the locked `inventory.quantity_on_hand` by 1 only after the insert succeeds.
  - `PERFORM record_audit('open_unit.open', 'open_unit', v_unit_id, NULL, v_after_row, 'rpc')` with `v_after_row` from `SELECT to_jsonb(u) FROM open_units u WHERE u.id = v_unit_id`. Return `v_unit_id`.

**`correct_open_unit(p_open_unit_id uuid, p_remaining_count int, p_reason text) RETURNS void`** — manager+ per D-12. Guard: `IF get_user_role() NOT IN ('manager','admin') THEN RAISE EXCEPTION 'AUTH_FORBIDDEN: manager or admin role required'; END IF;` (the `process_refund` shape). Then:
  - Require a non-blank `p_reason` — raise `VALIDATION_ERROR: reason is required` otherwise. A correction with no reason is exactly the unaudited-shrinkage hole T-27-10 covers.
  - Lock the target row `FOR UPDATE`; raise `NOT_FOUND: open unit % does not exist` if absent, and `VALIDATION_ERROR: open unit % is not active` if its status is not `'active'` (correcting a closed unit would silently reopen stock).
  - Validate `p_remaining_count` is between 0 and the parent product's `units_per_package` inclusive; raise `VALIDATION_ERROR` outside that range. Capture `v_before_row` before the update.
  - Update `remaining_count`, `updated_at`; when the corrected value is 0, also set `status = 'exhausted'`, `closed_at = now()`, `closed_by = auth.uid()`, `closed_reason = 'corrected_to_zero'` so the partial unique index frees the product for a fresh unit.
  - `PERFORM record_audit('open_unit.correct', 'open_unit', p_open_unit_id, v_before_row, v_after_row, 'rpc')` — both the old and new counts must be recoverable from the audit row, which is why the before/after sandwich is mandatory here rather than optional.

**`void_open_unit(p_open_unit_id uuid, p_reason text) RETURNS void`** — manager+ per D-12, same guard and same non-blank-reason requirement. Lock the row `FOR UPDATE`; require `status = 'active'`; set `status = 'void'`, `remaining_count = 0`, `closed_at = now()`, `closed_by = auth.uid()`, `closed_reason = p_reason`, `updated_at = now()`. Do NOT return the package to `inventory` — D-10 frames voiding as abandoning a physically opened box (damage, miscount), so the package is already gone; returning it would fabricate stock. `PERFORM record_audit('open_unit.void', 'open_unit', p_open_unit_id, v_before_row, v_after_row, 'rpc')`.

All three: `SECURITY DEFINER` with `SET search_path = public`, `GRANT EXECUTE ON FUNCTION ... TO authenticated` (RLS restricts direct table writes to manager/admin, and these functions are the sanctioned bartender path — the `stock_movements` + `record_stock_movement` arrangement already in this schema). Every audit write goes through `record_audit`; the legacy singular-named audit table described in 27-RESEARCH.md Pitfall 1 is not a write target in this migration.

| bartender client -> `correct_open_unit` / `void_open_unit` | A bartender can call any granted RPC directly with the browser devtools console or a raw HTTP request; the client PIN dialog is not in the path. |
