<objective>
Build the three user actions the Open-Units tab exposes, each as its own `features/` folder with one mutation wrapper plus one UI trigger, following this codebase's one-action-per-folder convention.

Purpose: the RBAC split is the whole point of separating them. D-11 puts "open a new unit" at bartender+ because it is high-frequency and low-risk at a busy bar, so it gets a plain button with no PIN friction. D-12 puts count correction and early void at manager+ because both are stock write-off vectors, so each gets a `ManagerPinDialog` in front of it. Building them before the tab (plan 27-08) means the tab composes finished, individually-testable actions instead of growing three inline flows.

On `ManagerPinDialog`'s `requiredAction` prop: use `adjust_inventory` deliberately. 27-RESEARCH.md Pitfall 4 documents that the existing negative-stock override flow in `CartPanel.tsx` passes `void_order` instead — a loose choice made when any manager-gated action would work mechanically. That is a pre-existing quirk, not a convention to replicate: `adjust_inventory` is manager+, matches D-12's stated tier word-for-word, and produces an accurate denial tooltip. No new `StaffAction` is minted — `adjust_inventory` already exists in `src/shared/lib/rbac.ts`.

Output: three feature folders, one component test, and i18n keys in both locales.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bartender at a terminal -> manager-gated dialog | The PIN prompt is client-side and therefore bypassable by anyone with devtools; it shapes behaviour, it does not enforce it. |
| user-entered count / reason -> RPC | Form validation is a convenience layer over the RPC's own guards. |
