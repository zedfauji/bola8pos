<objective>
Make the two new `products` columns writable from the existing admin product form, so the phase is usable without hand-written SQL.

Purpose: `consume_open_unit` keys entirely off `products.parent_product_id` (is this a loose piece?) and `products.units_per_package` (how many pieces does a fresh unit hold?). Plan 27-02 created the columns; nothing yet sets them. Without this plan the phase is reachable only by an operator running an `UPDATE products` statement by hand, which fails reachability: D-02 says units-per-package is "configured once on the parent product", and D-04 says any product can be flagged as sells-via-open-units — both are admin actions, and both need a field.

This is deliberately the *existing* form, not a new screen. It already handles nullable scalars (`sku`, `barcode`, `imageUrl`) and already sits behind the `manage_products` RBAC gate, so two fields plus two lines in each of three mappers is the whole change.

D-03 is a negative requirement and gets a negative check: the loose product's price is whatever the admin types into the existing base-price field. No code in this plan reads a package product's price, and no code divides anything by `units_per_package`.

Output: two new form fields, three extended mappers, and matching i18n keys in both locales.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin form input -> `products` columns | An operator-entered units-per-package value becomes the starting `remaining_count` of every future unit for that product; a bad value silently mis-states stock for the life of the product. |
| admin form input -> `parent_product_id` | This column is the predicate that routes an order line into `consume_open_unit`; setting it on the wrong product silently starts depleting the wrong package. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-17 | Input Validation (V5) | units-per-package entered as 0 or negative | medium | mitigate | Three layers: the form's below-minimum `fieldErrors` block, plan 27-05's `z.number().int().positive().nullable()`, and the table's `CHECK (units_per_package IS NULL OR units_per_package > 0)`. A zero would otherwise make `consume_open_unit`'s loop unable to make progress (its iteration guard is the last resort). |
| T-27-18 | Tampering (data integrity) | a product set as its own parent, or linked to an unconfigured parent | medium | mitigate | The selector excludes the product being edited and offers only products whose units-per-package is set, so the illegal pairs are unselectable rather than validated after the fact. |
| T-27-19 | Elevation of Privilege | non-admin editing open-unit product configuration | low | accept | The form is already reachable only through the `manage_products` RBAC gate (manager+) and the Settings catalog surface; this plan adds fields inside that existing boundary and no new entry point. |
| T-27-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install occurs in this plan — 27-RESEARCH.md `## Package Legitimacy Audit` records the gate as not triggered. |
