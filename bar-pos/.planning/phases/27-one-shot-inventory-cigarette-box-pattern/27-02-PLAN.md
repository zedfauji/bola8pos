Proving that spine on the executor's best early-context tokens means an architectural dead-end surfaces after one commit rather than after eight. The admin tab (SC-3) is a *view* onto this spine; it cannot be right if the spine is wrong, and `consume_open_unit` auto-opens units on demand, so the sale path is genuinely exercisable without any UI.

This is production code, not a prototype — the migrations authored here are the ones that ship.

### Three open questions from 27-RESEARCH.md, resolved here (not re-opened)

1. **`consume_open_unit` is invoked from *inside* `deplete_for_order_item`, not as a second client-callable RPC** (27-RESEARCH.md Open Question 1 / A1). Rationale: `deplete_for_order_item` is already the single chokepoint that order placement, voiding, refund-restock, and negative-stock override all funnel through, so nesting gets all four paths for free with zero new client wiring. The alternative — a sibling RPC — requires teaching 3+ client call sites about it, which is the exact bug class this codebase has already shipped once (the CR-01 omission fixed in `20260707000001_deplete_for_order_item_v4_...sql`).
2. **Multi-quantity loose-piece lines use the loop-based auto-transition design** (Open Question 2 / A4 / Pitfall 3). A single order line of quantity 3 against a unit holding 1 remaining piece consumes the last 1, marks that unit exhausted, auto-opens the next, and consumes 2 from it — all inside one atomic call. Rationale: this is the correct reading of SC-2's "auto-transitions to a new unit when exhausted", and the loop degrades to a single iteration when quantity is 1, so it costs nothing in the common case. It is NOT simplified to a block-if-quantity-exceeds-remaining design.
3. **Refund/void (`p_direction = -1`) credits back to whichever unit is currently active, capped at the parent product's `units_per_package`, discarding any remainder** (Open Question 3). Rationale: loose pieces are fungible and D-06 explicitly removes any low-count precision UI, so tracking a refund back to the exact physical unit it was drawn from buys nothing. If no unit is active, the credit is discarded rather than resurrecting an exhausted row (which would fabricate stock that is physically already gone) — the discard is recorded in the audit detail so the write-off is not silent.

Additionally resolved from 27-CONTEXT.md's Claude's-Discretion block: `open_units` does **not** integrate with the `stock_movements` ledger. That ledger's only mutation primitive locks the `ingredients` table and its idempotency index is keyed on `(ref_type, ref_id, ingredient_id)` — neither shape fits a per-package piece counter (27-RESEARCH.md Pitfall 2). `open_units` tracks its own state with its own `FOR UPDATE` locks; the one place package-level stock moves (auto-open consuming a box) writes the `inventory` table directly under a lock.

Output: 4 applied migrations, 6 new audit action strings, and one green end-to-end integration test.

**`20260729000003_consume_open_unit_rpc.sql`** — `CREATE OR REPLACE FUNCTION consume_open_unit(p_product_id uuid, p_qty int, p_order_item_id uuid, p_direction smallint, p_allow_negative boolean DEFAULT false) RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path = public`. `p_product_id` is the LOOSE product's id. Body:
  - Resolve `SELECT parent_product_id, ... INTO v_parent_id FROM products WHERE id = p_product_id`; if `v_parent_id IS NULL`, `RETURN` immediately — a product that is not a loose piece is a no-op, which is what makes the chokepoint branch in v5 safe for every other product in the catalog.
  - Read the parent's `units_per_package INTO v_per_package`; if it is NULL, raise `VALIDATION_ERROR: parent product % has no units_per_package configured` (a loose product whose parent was never configured is a data error, not a silent no-op).
  - No independent role guard: this function is only ever reached through `deplete_for_order_item`, which already raises `AUTH_FORBIDDEN` for null-role and kitchen callers. Do not `GRANT EXECUTE` to `authenticated` — there is deliberately no client call site (see resolved question 1 in the objective).
  - `p_direction = -1` (refund/void) branch: lock the active row for `v_parent_id` with `SELECT ... FOR UPDATE`; if found, set `remaining_count = LEAST(remaining_count + p_qty, v_per_package)` and record an `open_unit.deplete` audit row whose detail jsonb carries `direction: -1`, the credited amount, and the discarded remainder when the cap truncated it. If no active row is found, credit nothing and record the same action with a `credit_discarded` detail — resurrecting an exhausted unit would fabricate pieces that are physically gone. Then `RETURN`.
  - `p_direction = 1` (sale) branch: `WHILE v_remaining_qty > 0 LOOP`. Each iteration takes the active row for `v_parent_id` with `SELECT ... FOR UPDATE`. On `NOT FOUND`, auto-open: lock the parent's `inventory` row with `SELECT quantity_on_hand ... FOR UPDATE` (the client-side unlocked read-then-write in `src/entities/inventory/model/queries.ts` is a known pre-existing race — do not mirror it server-side, per 27-RESEARCH.md Pitfall 1's sibling note); if `quantity_on_hand < 1`, raise `INVENTORY_NEGATIVE: no unopened package available for product %` unless `p_allow_negative` is true, in which case open the unit anyway, let the package count go to `quantity_on_hand - 1`, and record an `open_unit.override` audit row capturing the bypass; otherwise decrement `quantity_on_hand` by 1, `INSERT` a fresh `open_units` row with `remaining_count = v_per_package`, `status = 'active'`, `opened_by = auth.uid()`, record `open_unit.open`, and `CONTINUE` so the loop re-selects the row it just created.
  - With a row in hand, `v_take := LEAST(v_remaining_qty, v_unit.remaining_count)`; `UPDATE open_units SET remaining_count = remaining_count - v_take` and, when that lands on zero, also set `status = 'exhausted'`, `closed_at = now()`, `closed_reason = 'exhausted'`; `updated_at = now()` always. Record `open_unit.exhaust` on the zero transition. Decrement `v_remaining_qty` by `v_take` and loop. This loop is what makes a quantity-3 line spanning two units correct (resolved question 2) — a bare `remaining_count - p_qty` with a negativity guard is the wrong design.
  - Emit exactly one `open_unit.deplete` audit row per call (not per iteration) once the requested quantity is fully consumed, with `order_item_id` and total qty in the detail jsonb.
  - All audit writes go through `PERFORM record_audit(<action>, 'open_unit', <unit id>, <before jsonb>, <after jsonb>, 'rpc')`. `record_audit` swallows its own exceptions, so it can never abort the caller. The legacy singular-named audit table described in 27-RESEARCH.md Pitfall 1 is deprecated and is not a write target for any statement in this migration. Also note that the `ingredients`-table stock primitive described in 27-RESEARCH.md Pitfall 2 cannot reach `open_units` or `inventory` rows and is therefore not invoked anywhere in this function — the locks here are hand-written against the two tables that actually hold the counters.
  - Add a `LOOP` iteration guard (e.g. bail with a `VALIDATION_ERROR` after `p_qty + 2` iterations) so a mis-set `units_per_package` of zero cannot spin forever.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client (POS terminal) -> `deplete_for_order_item` RPC | Untrusted `p_order_item_id` / `p_allow_negative` cross here; `p_allow_negative` is a privilege-bearing flag a client could set on its own. |
| two concurrent terminals -> same `open_units` row | Simultaneous sales of the last remaining piece cross here; correctness depends entirely on database-level serialization. |
| `consume_open_unit` -> `audit_logs` | The only record of who consumed/overrode a unit; actor identity must be server-derived. |
