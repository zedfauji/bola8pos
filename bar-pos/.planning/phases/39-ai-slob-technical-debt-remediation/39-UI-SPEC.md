## Phase Classification: No New UI Work

This phase (`39-ai-slob-technical-debt-remediation`) is a **pure code-quality/reliability remediation phase**, not a visible-feature phase. Per `39-CONTEXT.md` `<specifics>`: *"No particular UI/UX references — this is a pure code-quality/reliability phase, not a visible feature."*

Scope (from `39-CONTEXT.md` `<decisions>` D-01):

1. **E2E triage** (147 Blocking-tier findings: 94 failed + 53 skipped) — classify each into infra/flaky (defer to Phase 38), real regression (fix), or obsolete test (update/remove).
2. **Knip unlisted-deps fix** (34 Blocking-tier findings) — `package.json` dependency declarations, not UI.
3. **Knip dead-code deletion** (High-tier 1917 + Medium-tier 37 = 1954 findings) — deleting confirmed-unused files/exports/types after a false-negative sanity check (D-07), explicitly skipping the Medium-tier 37 suspected-false-positive `shared/ui`/Storybook findings per D-08.

None of these introduce a new screen, component, interaction pattern, copy string, or visual treatment. Dead-code removal touches files physically located in `shared/ui`, `widgets`, and `features` layers (which is why the UI safety gate flagged this phase), but the *nature* of the change in those files is subtractive (deleting confirmed-unused exports/files) — it is not additive UI design work.

**This UI-SPEC therefore does not declare a new design contract.** It exists to record that fact explicitly and to constrain the planner/executor with guardrails so dead-code removal and E2E fixes don't drift into inventing UI changes.

## Guardrails for Planner and Executor

These are the operative rules this UI-SPEC exists to enforce, given the phase touches files across `shared/ui`, `widgets`, and `features`:

1. **No new components.** Do not create new files under `src/shared/ui/`, `src/widgets/`, or `src/features/` as part of this phase. Only delete confirmed-dead files/exports or fix a confirmed real E2E regression in an existing file.
2. **No new styles or tokens.** Do not touch Tailwind classes, CSS variables, or `components.json` for aesthetic reasons. A dead-code deletion may remove a class along with its dead JSX, but must not restyle the surrounding markup.
3. **No new copy.** Any string literal touched during an E2E-regression fix must match what was already shipped (check the relevant prior phase's `CLAUDE.md`/`UI-SPEC.md`/git history for the original string) — never invent new UX copy.
4. **Dead-code deletions must preserve remaining behavior exactly.** Per `39-CONTEXT.md` D-07, run the sanity check for dynamic/string-based usage (router config, string-keyed lookups, Storybook auto-discovery per D-08) before deleting — a false-positive deletion that silently breaks a UI surface violates this contract as much as introducing unwanted new UI would.
5. **Route product-behavior bugs out, don't redesign in place.** Per D-03, any real product bug found during E2E triage beyond a trivial one-line same-root-cause fix gets filed as a todo — it does not get "fixed" by changing the UI's design/copy/interaction in this phase.
6. **If any task in this phase's plan appears to require a genuinely new component, new copy, or a visual redesign, stop and flag it** — that would be scope creep beyond `39-CONTEXT.md`'s locked decisions and needs a separate UI-SPEC / phase, not silent inclusion here.
