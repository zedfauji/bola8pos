<objective>
Resolve the FSD barrel question with one decision instead of 445 individual ones.

Recomputing the knip reports directly showed something the raw counts hide: 433 of the 918 line-level export and type findings live in `index.ts` barrel files — `src/entities/<slice>/index.ts`, `src/entities/<slice>/model/index.ts`, `src/features/<action>/index.ts` — spread across 64 files. Another 12 barrels are flagged dead as whole files. That is 445 findings, roughly 45% of the phase's remaining knip work, all of the same shape: a slice re-exports its public API, and knip flags each re-export that no consumer currently pulls through the barrel.

Those barrels are the codebase's declared architecture. CLAUDE.md documents the `app -> pages -> widgets -> features -> entities -> shared` import direction, `eslint-plugin-boundaries` enforces it, and 22 call sites import from `@entities/settings` alone. knip's own documentation says to ask whether it merely lacks visibility before deleting, and a public-API barrel is the canonical case where it does.

This plan settles that once, applies the answer uniformly, and republishes a knip baseline for the three plans that follow.

Purpose: prevent 445 findings from becoming 445 uncoordinated deletions that quietly narrow the codebase's architectural contract.
Output: a recorded decision, its uniform application, and a fresh post-decision baseline.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>How should the 445 FSD barrel findings be resolved — narrow the public API by deleting unused re-exports, or teach knip that slice barrels are declared entry points?</decision>
  <context>
    These 445 findings are about 45% of the phase's remaining knip work and they are all one shape. `src/entities/tab/index.ts` re-exports roughly 29 symbols as the slice's public API; knip flags each one no consumer currently imports *through the barrel*. Most of those symbols are alive and well — consumers just reach them by deep path instead.

    This is exactly the case knip's own documentation describes when it says to configure before deleting: the tool is reporting a visibility gap, not necessarily dead code. But the opposite reading is also legitimate — a public API nobody uses is a public API worth shrinking, and 39-CONTEXT.md D-07 authorizes deleting confirmed dead code.

    D-07 also rates dead-code deletion as **costly to reverse**: re-adding 433 re-export lines across 64 files after discovering a consumer means re-wiring, not just reverting one commit. That asymmetry is the reason this is a decision rather than a default.

    Task 1's measured import ratio should be read before choosing. If deep-path imports dominate, the barrel convention has already eroded in practice and option A is honest cleanup. If barrel-style imports dominate, the findings are mostly a visibility artifact and option B is correct.
  </context>
  <options>
    <option id="prune-barrels">
      <name>A — Prune: delete the unused re-export lines and the 12 whole-dead barrels</name>
      <pros>Genuinely reduces the finding count by 445. Shrinks each slice's public API to what is actually consumed. Requires no tooling config change. Fully honors D-07's "delete confirmed dead code" as written.</pros>
      <cons>Narrows an architectural contract that `eslint-plugin-boundaries` enforces and CLAUDE.md documents. A future consumer wanting `@entities/tab`'s full surface must re-add the export. Costly to reverse across 64 files. Highest-churn option for zero runtime effect.</cons>
    </option>
    <option id="configure-knip">
      <name>B — Configure: declare slice barrels as knip `entry` points, delete only the 12 whole-dead barrels</name>
      <pros>Matches knip's documented "configure first, delete last" guidance. Preserves the FSD public-API contract exactly. Stops future audits from re-reporting the same 433 findings every run. Near-zero reversal cost — one config edit. Still removes the 12 barrels nothing imports at all.</pros>

      <pros>Removes what is unambiguously dead — a re-export of a symbol that is itself flagged unused — while leaving live symbols reachable through their slice's public API. No config change. Middle reversal cost.</pros>
      <cons>Requires a per-finding cross-check between the barrel line and the underlying declaration, making this the most labor-intensive option. Leaves a residual finding count that later audits will keep reporting.</cons>
