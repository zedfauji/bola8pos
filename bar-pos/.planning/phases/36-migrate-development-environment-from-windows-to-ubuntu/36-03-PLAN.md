## Discovered during planning — read before starting

Two corrections to the framing in CONTEXT.md and RESEARCH.md. Neither reduces scope; both change what "done" can honestly mean.

1. **There is no existing Windows CI job to mirror.** D-11 describes mirroring one, but `.github/workflows/ci.yml` has exactly one job, `quality`, and it already runs on `ubuntu-latest` doing lint, typecheck, unit tests and audit. The only Windows pipeline is `release.yml`'s `publish-tauri` on a self-hosted Windows runner, which D-04 keeps untouched. So D-11's lint/typecheck/unit-test half is already satisfied today; the genuinely missing piece is a **native Tauri build on Linux**, which `ci.yml` never performs. That is what this plan adds.
2. **These workflows are in a directory GitHub does not read.** The git root is `bola8pos-kiro/` and the whole project sits in `bola8pos-kiro/bar-pos/`, so the workflow files live at `bar-pos/.github/workflows/`. GitHub Actions only reads `.github/workflows/` at the repository root, and there is no root-level `.github/` directory. These workflows therefore do not currently run at all. Relocating them is deliberately **out of scope**: moving `release.yml` would *activate* a Windows code-signing release pipeline that has never fired, which directly conflicts with D-04's instruction to leave the release pipeline alone. The relocation decision is raised for the user in plan 36-04.

Consequence: this plan's acceptance criteria verify the job **structurally and locally** (the YAML parses, the job and its steps exist and match the sibling `quality` job's conventions). They deliberately do not claim "the CI job passes on GitHub", because it cannot run until the relocation question is answered. Separately, note that `npm run tauri build` invokes `beforeBuildCommand` (`npm run build`, which runs `tsc`), and typecheck currently fails on 2 pre-existing errors — so even once relocated, this job stays red until those are fixed. Both blockers are pre-existing and OS-independent; record them, do not fix them here.

Job key `tauri-build`, display name `Tauri Native Build (Linux)`, `runs-on: ubuntu-latest`, and the same `defaults.run.working-directory: bar-pos` block the `quality` job uses. Steps, in order:

1. `actions/checkout@v4`.
2. `actions/setup-node@v4` with `node-version: '22'`, `cache: 'npm'`, `cache-dependency-path: bar-pos/package-lock.json` — identical to the `quality` job so both jobs share one npm cache.
3. `dtolnay/rust-toolchain@stable` — the ecosystem-standard Rust installer for GitHub Actions; faster and more cache-friendly than shelling out to rustup's curl installer inside CI.
4. `Swatinem/rust-cache@v2` with its `workspaces` input set to `bar-pos/src-tauri`. Note that `defaults.run.working-directory` applies to `run:` steps only, not to `uses:` action inputs, so this path must be written relative to the repository root. Without this cache every pull request pays a full cold Rust compile.
5. A `run:` step installing the Tauri Linux system libraries with `sudo apt-get update` followed by `sudo apt-get install -y` of exactly the same ten packages `scripts/setup-ubuntu.sh` installs: `libwebkit2gtk-4.1-dev`, `build-essential`, `curl`, `wget`, `file`, `libxdo-dev`, `libssl-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`, `pkg-config`. The two lists must stay identical so CI and the dev machine cannot drift apart.
6. `npm ci`.
7. `npm run tauri build -- --ci --no-bundle`. `--ci` suppresses interactive prompts; `--no-bundle` stops Tauri producing `.deb`/`.AppImage` artifacts that nothing downstream consumes and that D-01 explicitly does not ship.

Keep the file's existing two-space YAML indentation and its `- name:` / `uses:` step style so the two jobs read consistently.
