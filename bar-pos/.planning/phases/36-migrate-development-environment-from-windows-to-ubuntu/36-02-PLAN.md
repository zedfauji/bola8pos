## Discovered during planning — read before starting

Live probes on this checkout found three things `36-RESEARCH.md` did not:

1. **`.husky/` is gitignored.** `bar-pos/.gitignore` line 55 lists `.husky/`, and `git ls-files .husky` returns nothing. The hook files are untracked. This makes RESEARCH.md's proposed `.husky/* text eol=lf` attribute rule a **dead rule** — git attributes only affect tracked content — and it makes the executable-bit concern moot for the same reason. That is why the `.gitattributes` written here covers `*.sh` only.
2. **`core.hooksPath` is a stale absolute Windows path**: `C:\Users\giris\Documents\Code\Redesign-POS\More POS\bola8pos-kiro\.git\hooks`. Git hooks are therefore completely inert on this machine — and were inert on Windows too, since that value points at git's default hooks directory, not at husky's. Husky cannot self-repair it either: husky v9's installer returns `.git can't be found` and does nothing when run from `bar-pos/`, because the git root is one level above at `bola8pos-kiro/`.
3. **Repairing `core.hooksPath` right now would be actively harmful.** `.husky/pre-commit` runs `npx tsc --noEmit`, and typecheck currently fails with 2 pre-existing errors (`src/entities/tab/model/queries.ts:791`, `src/shared/lib/agent/rag.ts:60`). Activating hooks would block every commit in the repo, including this phase's own. **This plan therefore does NOT touch `core.hooksPath`.** Whether to activate hooks at all is routed to the user as a decision checkpoint in plan 36-04.

RESEARCH.md also proposed a blanket `* text=auto eol=lf` plus `git add --renormalize .`. That is deliberately **not** done here: 739 of 1694 tracked files currently have CRLF endings, so a blanket renormalize would produce a 739-file churn commit on top of a working tree that already carries ~100 modified files. Markdown, JSON and TypeScript with CRLF break nothing on Linux — only shell shebangs do. Narrowing to `*.sh` fixes the actual breakage and reduces no D-XX decision.
