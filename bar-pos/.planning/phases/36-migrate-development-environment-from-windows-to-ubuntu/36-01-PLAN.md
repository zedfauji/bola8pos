<objective>
Tracer slice for Phase 36: take this Ubuntu machine from "no Rust, no webkit2gtk, Windows-only node_modules" to "the native Tauri shell compiles and links here", and capture that path as a committed, repeatable script.

Purpose: This is the phase's core goal (D-03, D-07, D-08, D-09). Every other plan in this phase is documentation or CI mirroring of what this plan proves works.
Output: `bar-pos/scripts/setup-ubuntu.sh`, a Linux-native `node_modules`, and a linked `src-tauri/target/debug/bar-pos` ELF binary.

## Discovered during planning — read before starting

Planning ran live probes on this machine. Three facts differ from what `36-RESEARCH.md` assumed:

1. **`node_modules/` is a Windows install.** Only `@esbuild/win32-x64`, `@rollup/rollup-win32-x64-*` and `@tauri-apps/cli-win32-x64-msvc` are present; `@tauri-apps/cli-linux-x64-gnu` is absent. `npx tauri` currently dies with `Cannot find native binding`. `package-lock.json` *does* contain all the Linux optional-dependency entries, so a clean `npm ci` fixes it. RESEARCH.md never ran the Tauri CLI, so it missed this — it is the first blocker, before Rust or apt.
2. **`npm run build` cannot succeed right now.** `npx tsc --noEmit` fails with 2 pre-existing type errors (`src/entities/tab/model/queries.ts:791`, `src/shared/lib/agent/rag.ts:60`). These are OS-independent and out of this phase's scope. That is why this plan proves the native toolchain with `cargo build` (which does not invoke `tsc`) rather than `npm run tauri build` (whose `beforeBuildCommand` is `npm run build`). Do not "fix" those two errors here.
3. **`src-tauri/src/commands/printer.rs` is already correctly cfg-gated** (`#[cfg(target_os = "windows")]` with matching `#[cfg(not(target_os = "windows"))]` fallbacks), so the Windows printing code compiles away cleanly on Linux. D-02 needs no code change.

  <action>
Create `bar-pos/scripts/setup-ubuntu.sh` and make it executable (`chmod +x`). Write it as a single idempotent bash script with `#!/usr/bin/env bash` and `set -euo pipefail`, structured in this order:

1. `cd` to the project directory relative to the script's own location (`dirname "$0"` then `..`) so the script behaves identically whether invoked from the repo root or from `bar-pos/`. This matches the `cd bar-pos && ...` convention already used in `.cursor/environment.json`.
2. OS guard: grep `/etc/os-release` for a line matching `^ID(_LIKE)?=.*(ubuntu|debian)`; on no match, print a message naming the script and the detected OS to stderr and `exit 1`. Then echo the detected `VERSION_ID` and `VERSION_CODENAME` purely as diagnostic output. Per D-06 do NOT branch any package name on the version — the required package set is identical across Ubuntu 22.04 through 26.04.
3. `sudo add-apt-repository -y universe || true` (defensive no-op when universe is already enabled; `libwebkit2gtk-4.1-dev` and `libayatana-appindicator3-dev` live in universe on minimal images), then `sudo apt-get update`, then a single `sudo apt-get install -y` of exactly these ten packages: `libwebkit2gtk-4.1-dev`, `build-essential`, `curl`, `wget`, `file`, `libxdo-dev`, `libssl-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`, `pkg-config`. Do not hand-roll a `dpkg -s` check-before-install loop — `apt-get install` is already idempotent. The 4.0-series variant of the webkit2gtk dev package must not appear anywhere in the script, not even as a compatibility fallback or an explanatory comment: it is a Tauri v1-era package that no longer exists in current Ubuntu archives, and an acceptance criterion greps the finished script to confirm its absence.
4. Node preflight: if `command -v node` fails, print an error naming `nvm` or `fnm` as the install route and `exit 1`. Per D-09 and RESEARCH.md Open Question 2, this script must NOT install Node itself.
5. Stale-Windows-`node_modules` detection: if a `node_modules` directory exists but `node_modules/@tauri-apps/cli-linux-x64-gnu` does not, print a clearly-worded error explaining the checkout carries Windows-only native bindings, name `rm -rf node_modules && npm ci` as the exact remediation, and `exit 1`. Do not print npm's own misleading advice about deleting `package-lock.json` — the lockfile already contains the correct Linux optional-dependency entries.
6. Rust toolchain, guarded by `command -v cargo`: when cargo is already present, echo `cargo already installed: <version>` and skip. When absent, prefer the apt-signed path — if `apt-cache policy rustup` reports a real Candidate (i.e. not `(none)`), `sudo apt-get install -y rustup` then `rustup default stable`; only when there is no apt candidate (older Ubuntu releases), fall back to the official installer `curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y`. After either path, `source "$HOME/.cargo/env"` guarded so the script does not fail when that file is absent. The apt-first ordering is the mitigation for threat T-36-01 below: it keeps toolchain provenance inside Ubuntu's signed archive instead of piping a remote script to a shell.
7. Final sanity check: run `npx @tauri-apps/cli info` (the local devDependency CLI, not `npx --yes`, so it cannot silently fetch a different version). This is the one command that cross-checks Node, Rust, and the webkit2gtk system libraries together — do not hand-roll an equivalent multi-step verifier.

Then execute the path the script describes, in this order:
  a. `chmod +x scripts/setup-ubuntu.sh` and run `bash scripts/setup-ubuntu.sh` from `bar-pos/`. It is expected to stop at step 5 on the first run because `node_modules` is currently a Windows install.
  b. Apply the remediation the script names: `rm -rf node_modules && npm ci`.
  c. Re-run `bash scripts/setup-ubuntu.sh` so it proceeds through the Rust install and the `@tauri-apps/cli info` sanity check.
  d. Prove the native layer end-to-end with `cargo build --manifest-path src-tauri/Cargo.toml`. Use `cargo build` rather than `npm run tauri build` because the latter's `beforeBuildCommand` is `npm run build`, which currently fails on 2 pre-existing `tsc` errors unrelated to this phase.

Commit only `scripts/setup-ubuntu.sh` — `node_modules/`, `dist/` and `src-tauri/target/` are gitignored build state.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote install script -> local root shell | `sh.rustup.rs` content executed with the developer's shell, and `apt-get` executed under `sudo` |
| Ubuntu apt archive -> local system libraries | signed Canonical archive supplying webkit2gtk and friends |
| npm registry -> `node_modules` native bindings | `npm ci` fetching platform-specific optional dependencies |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-36-01 | Tampering | rustup install path in `scripts/setup-ubuntu.sh` | medium | mitigate | Prefer `sudo apt-get install -y rustup` (Ubuntu-signed archive) whenever `apt-cache policy rustup` reports a candidate; fall back to the official installer only on releases without the package, and then only via `curl --proto '=https' --tlsv1.2 -sSf` so TLS downgrade and plaintext MITM are refused. |
| T-36-02 | Elevation of Privilege | `sudo` calls inside an unattended setup script | medium | mitigate | The script is a committed, PR-reviewable repo file run interactively by a developer from a local checkout — never fetched-and-piped from a URL. `sudo` is scoped to `add-apt-repository` and `apt-get` only; no `sudo` wraps the rustup or npm steps. |
| T-36-SC | Tampering | apt + npm dependency installs | medium | accept | Zero new npm/PyPI/crates packages are introduced (36-RESEARCH.md `## Package Legitimacy Audit`), so the slopsquatting gate does not apply. `npm ci` installs only lockfile-pinned optional dependencies already present in `package-lock.json`; apt packages come from Canonical's signed archive. No `[ASSUMED]`/`[SUS]`/`[SLOP]` package needs a human legitimacy checkpoint. |
| T-36-03 | Information Disclosure | `npx @tauri-apps/cli info` output | low | accept | Prints local toolchain versions and paths only; it runs on the developer's own terminal and is not published. |

ASVS level 1, block-on severity high. No high or critical threat is present: this plan touches no application code, no user data, no auth surface, and does not change the shipped Windows binary (D-01).
</threat_model>
