<objective>
Add the `is_temp` column and the `'floating'` type value to the renamed relation, and install the event-driven trigger that soft-deletes a floating resource the moment its session stops.

Purpose: D-04 chose an immediate DB trigger over an idle-timeout scanner, and soft-delete over hard-delete because `pool_sessions.table_id` carries ON DELETE RESTRICT — a floating table that was ever used can never be hard-deleted. Everything this needs already exists: the `is_deleted` and `deleted_at` columns landed in a prior phase and are currently unused by any resource code path, and the SELECT policy already filters on `is_deleted = FALSE`, so a soft-delete presents to clients as the row simply vanishing.

This plan also closes the phase's one real validation gap. VALIDATION.md flags that no SQL test harness exists for the trigger. It does exist, in a form this repo already uses: a dedicated vitest `integration` project (`npm run test:integration`, `src/**/*.integration.test.ts`, excluded from `npm run test`) with an env-guarded `describe.skipIf` convention, exercised today by the pool-promotions and tip-distribution RPC tests. No pgTAP harness is needed.

Output: two migrations applied, Zod extended, and an integration test proving SC-2 in both the floating and the non-floating direction.
</objective>

Write two migrations, keeping one concern per file to match this repo's convention.

The first migration adds the column and extends the type constraint. Add `is_temp BOOLEAN NOT NULL DEFAULT FALSE` using `ADD COLUMN IF NOT EXISTS`; the default is what preserves every existing row as non-floating without a backfill. Then replace the `table_type` CHECK so it admits `'pool'`, `'carom'`, `'consumption'`, and `'floating'` — all four, since dropping any pre-existing value would invalidate live rows. The existing constraint was declared inline, so Postgres generated its name; resolve the real name from `information_schema.table_constraints` or `\d` against the live database before writing the DROP, and do not guess it. Guard the drop with IF EXISTS and name the new constraint explicitly so it is addressable later. Follow the analog's header-comment convention: state why a TEXT CHECK is used rather than a new enum, and note that the default preserves existing rows.

Do not add `is_deleted` or `deleted_at` — they already exist from the soft-delete migration.

The second migration creates the trigger function and the trigger. The function is `deactivate_floating_resource()`, returning TRIGGER, in plpgsql, declared `SECURITY DEFINER` with `SET search_path = public`. The definer declaration is defense in depth: its only realistic caller is already a definer function, but pinning the search path is this repo's standing convention for elevated functions and is what prevents a caller-controlled schema from shadowing the relations the body references.

The body fires only on the transition into stopped: proceed when `NEW.stopped_at` is non-null and `OLD.stopped_at` is null. That guard is load-bearing — without it, any later UPDATE touching an already-stopped session would re-run the soft-delete. Inside the guard, UPDATE the resources relation setting `is_deleted` true, `deleted_at` to now, `status` back to available, and `current_session_id` to null, matching on `NEW.table_id` and narrowed to rows that are currently temp and not already deleted. The `is_temp` predicate is what protects every ordinary table from being retired by a normal session stop. The not-already-deleted predicate makes the operation idempotent. Return NEW.

Never issue a DELETE against the resources relation here. The session that just stopped holds a `table_id` reference under ON DELETE RESTRICT, so a hard delete would raise a FK violation and abort the enclosing stop-session transaction, and it would also destroy the historical reference that reports depend on.

Attach it as an AFTER UPDATE row-level trigger on `pool_sessions` named `deactivate_floating_resource_on_session_stop`.

Create exactly one trigger. Do not add a companion trigger on `tabs`: a tab linked to a running session cannot reach closed state today, because the close-tab guard in the read_first list returns a session-still-running error before attempting the update. Session stop is therefore the only closure path that exists, and a second trigger would be scope the current architecture does not need. Consumption-type tables are not an exception — they go through the same session start and stop flow, since the billing path reads only the rate and first-hour mode and is agnostic to type.

Note for the reader that the existing hard-delete mutation on the resource entity survives unchanged and is not in conflict: it is guarded to fire only on a row that is available with no current session, meaning a table that never had a session. The two deletion mechanisms coexist deliberately and must not be unified.
