<objective>
Rename the `pool_tables` relation to `resources` at the database level and prove the three PL/pgSQL functions whose bodies literally reference the old name still work afterwards.

Purpose: this is the phase's tracer — the single riskiest architectural bet (D-01's one-way rename) proven end-to-end through DDL, PL/pgSQL RPC, and generated types before any floating-table feature work is layered on top. Postgres does not rewrite function body text on `ALTER TABLE ... RENAME` (Pitfall 3), so a rename that skips the function recreations silently breaks pool billing and tab transfers at runtime, not at migration time.

Output: one rename migration applied to the live database, regenerated `supabase.types.ts`, and a hand-updated `supabase-contracts.ts` shim in the same commit.

**Declared transient state:** at the end of this plan the React application is knowingly broken at typecheck and at runtime — every stale call site and the regenerated `Tables<...>` lookups reference a relation that no longer exists. This is inherent to a relation rename: no ordering keeps both typecheck and runtime green across it. Plan 02 (Wave 2) is the restoration gate and must run immediately after. A red `npm run typecheck` at the end of this plan is expected, not a defect — Plan 01's verification is database-level only.

The security requirement pins the type regen here rather than in Plan 02: generated types and the hand-maintained shim must land in the same commit as the migration, not a follow-up (threat T-26-02).
</objective>

D-01 is rated one-way: once the relation is renamed and roughly 23 source files plus three PL/pgSQL function bodies depend on the new name, reverting means a second full rename pass across the same surface. There is no cheap undo.

Two objects sit outside D-01's literal wording, and RESEARCH.md Open Question 1 asks for an explicit ruling rather than a silent planner decision:

1. The Postgres enum type `pool_table_status` (`supabase/migrations/20260414000001_enums.sql:8`), which types the `status` column.
2. The table `pool_table_transfers` and its columns `from_pool_table_id` / `to_pool_table_id` (`supabase/migrations/20260420000003_transfers.sql`), a transfer-audit log with two FKs into the renamed relation. Its RLS policies are named "Staff can read pool table transfers" and "Staff can insert pool table transfers".

Both are OID-linked, so both keep working untouched. The question is naming debt, not correctness. Note that `transfer_tab` and `transfer_pool_session` must be recreated regardless of this choice (Pitfall 3), so folding the transfers rename in costs almost nothing extra.

Not in scope under either option: the `settings` row key collision (Pitfall 2 — a coincidental string collision with an unrelated config-blob key), the `pool_sessions` relation name (D-01 scopes only the FK relationship from it, not the relation itself), and all user-facing copy and routes (D-02).

Write one migration implementing the rename scope confirmed in Task 1. The header comment must state why the function recreations live in this same file: Postgres stores PL/pgSQL source as opaque text in `pg_proc.prosrc` and does not rewrite it on relation rename, so a rename without them breaks pool billing and transfers at first invocation, not at migration time.

DDL, in this order:

1. `ALTER TABLE pool_tables RENAME TO resources`.
2. Rename the three indexes to `idx_resources_number`, `idx_resources_status`, `idx_resources_current_session_id`.
3. Rename constraints: `number_positive` to `resources_number_positive`, `rate_positive` to `resources_rate_positive`, `fk_pool_tables_current_session` to `fk_resources_current_session`. This FK constraint name is load-bearing — it is consumed as a PostgREST embed hint by the entity query layer that Plan 02 updates, so the new name must be exactly `fk_resources_current_session`.
4. `ALTER TRIGGER update_pool_tables_updated_at ON resources RENAME TO update_resources_updated_at`.
5. Rename the five live RLS policies to `resources_select_authenticated`, `resources_update_bartender`, `resources_insert_manager_admin`, `resources_update_manager_admin`, `resources_delete_manager_admin`. Use `ALTER POLICY ... RENAME TO` — do not drop and recreate, which risks altering the USING and WITH CHECK expressions. The `is_deleted = FALSE` predicate on the SELECT policy must survive byte-identical; Plan 03's auto-deactivate behavior depends on it hiding retired rows.
6. If Task 1 selected `full`: `ALTER TYPE pool_table_status RENAME TO resource_status`; `ALTER TABLE pool_table_transfers RENAME TO resource_transfers`; rename its columns to `from_resource_id` and `to_resource_id`; rename its two RLS policies consistently. If Task 1 selected `table-only`, skip step 6 entirely.

Then `CREATE OR REPLACE FUNCTION` for exactly three functions, each reproduced from the read_first source that is currently live, with only relation and column names swapped and every other line byte-identical:

- `stop_pool_session` — its body reads `rate_per_hour` from the renamed relation and updates it.
- `transfer_tab` — writes the transfers audit row and updates `current_session_id` on the renamed relation.
- `transfer_pool_session` — use the body from `20260713000002_fix_transfer_pool_session_version_bump.sql`. Reproducing the older body from `20260420000003_transfers.sql` would silently regress the version-bump fix.

Each recreated function keeps its existing `SECURITY DEFINER` and `SET search_path = public` declarations. Do not add, remove, or reorder parameters — clients call these with a fixed argument list, and a changed signature creates an overload instead of replacing the function.

Add no columns and no triggers here. The `is_temp` column, the `'floating'` type value, and the auto-deactivate trigger are Plan 03's scope, deliberately split so this rename is independently verifiable.

Write no DML in the DDL section. Row data survives `ALTER TABLE ... RENAME` unchanged; any UPDATE or INSERT of row data here would be a bug. (The recreated function bodies legitimately contain UPDATE statements — that is their existing logic, not new DML.)

Do not touch `pool_sessions` — its name is unchanged and its `table_id` FK re-targets by OID automatically.
