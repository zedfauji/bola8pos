  <action>
    Create `src/shared/lib/format.ts` as a pure, dependency-light module in the `shared` FSD layer.

    Import `getCurrentLocale` from `@shared/lib/i18n` and the `Locale` type from `@shared/lib/domain` (type-only import — `@typescript-eslint/consistent-type-imports` is set to `type-imports`).

    Declare a module-private `CURRENCY_SYMBOL: Record<Locale, string>` mapping `'es-MX'` to the two-letter-prefixed symbol `MX$` and `'en-US'` to the bare `$`, per D-01. Do not export it.

    Export `formatMoneyIn(locale, amount, options?)`: compute `isNegative` from `amount < 0`; build the numeric portion with `new Intl.NumberFormat(locale, { minimumFractionDigits: 2, maximumFractionDigits: 2 }).format(Math.abs(amount))`; return sign + `CURRENCY_SYMBOL[locale]` + numeric, where sign is `-` when negative, `+` when `options?.showSign` is set on a non-negative amount, and empty otherwise. Never pass a `style` option to `Intl.NumberFormat` — per 28-RESEARCH.md Pattern 2, `style: 'currency'` emits ISO-code output for es-MX and can never yield the D-01 symbol.

    Export `formatMoney(amount, options?)` as a one-line delegation to `formatMoneyIn(getCurrentLocale(), amount, options)`. Its own signature takes no locale parameter, per D-06. `formatMoneyIn` exists so the two locale-parameterized consumers migrated in plan 02 (`receipt-format.ts`, `exporters/pdf.tsx`) can keep formatting against the transaction's own locale instead of the live UI session — this resolves 28-RESEARCH.md Pitfall 1 / Open Question 2 in favor of the parameterized helper rather than a documented simplification.

    Export `formatPercent(value, options?)`: format `value` with `new Intl.NumberFormat(getCurrentLocale(), { minimumFractionDigits: 0, maximumFractionDigits: options?.decimals ?? 1 })` and append a percent sign. No symbol map is involved.

    Export `parseMoneyInput(input)`: trim the input, test it against an anchored pattern accepting an optional leading minus, one or more digits, and an optional fractional part of one or two digits; return `Number(trimmed)` on match and `null` otherwise. Reject-on-ambiguity is the contract — never coerce a non-matching string to a number. Do not couple this to `MoneySchema` (28-RESEARCH.md Pitfall 5: `MoneySchema` is `nonnegative()`, but negative money is first-class in this app; a caller wanting non-negativity composes the schema itself). Do not wrap the return in `Result<T>` — D-04 is explicit that the contract is a bare `null`.

    Give each export a JSDoc block. On `parseMoneyInput`, state in the JSDoc that callers MUST branch on `null` and that the function never yields a fallback number, so a missed check is a compile-visible type error rather than a silent zero.

    Create `src/shared/lib/format.test.ts` covering every case in the behavior block. Use the `await i18n.changeLanguage('en-US')` / assert / `await i18n.changeLanguage('es-MX')` reset pattern from `src/shared/lib/i18n/index.test.ts` for the locale-dependent assertions, and reset the language in an `afterEach` so no test leaks locale state into siblings. `formatMoneyIn` assertions do not need `changeLanguage` — assert both locales directly and additionally assert that `formatMoneyIn('en-US', ...)` is unaffected while the live language is es-MX.

    Also assert the half-cent rounding boundary: `formatMoney(12.555)` under Intl half-expand rounding rounds up to `12.56`, where the superseded fixed-point helper produced `12.55`. Pin the new value in a test so the change is recorded rather than discovered in production.
