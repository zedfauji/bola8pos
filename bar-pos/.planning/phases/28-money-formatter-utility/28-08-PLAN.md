<assumption_delta_decision>
**Signal:** `chosen` / "custom" — ROADMAP SC-3's phrase "Custom ESLint rule `no-raw-money-format`".

**Question:** promote the repo's lint-customization mechanism to a real ESLint rule plugin (`meta`/`create`/`context.report`, or an `eslint-plugin-*` package), or add this rule alongside the existing mechanism as a second selector array?

**Decision: add alongside.** `no-ui-drift.js` already established selector-array-spread-into-`no-restricted-syntax` as this repo's way of expressing a custom lint check, and it explicitly documents itself as not a rule plugin. Both of D-08's detection targets were verified during research to be expressible as esquery selectors against this repo's installed parser, so promotion buys no capability this phase needs while introducing the repo's first rule-plugin surface to maintain. If a future rule needs type-aware analysis or variable-name inspection, that is the point to reconsider promotion — and it would then be a deliberate mechanism change rather than a side effect of one rule.
</assumption_delta_decision>
