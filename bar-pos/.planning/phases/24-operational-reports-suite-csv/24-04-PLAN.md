<objective>
Close the un-audited-removal gap (D-06/D-07) and build the two deletions reports (D-05).
`remove_tab_item` replaces `useRemoveTabItem`'s 3-step client mutation (delete → check →
void) plus its long-standing inventory-restore TODO with a single atomic RPC that also
audits the removal — resolving two backlog items in one migration. The two deletions
report RPCs read the plural `audit_logs` table for the two financial-risk stages: variant
A (pre-send item removal, `order_item.remove`) and variant B (post-close correction,
`tab.edit_paid`).

Purpose: SC-1 (RPCs + order_item.remove audit) + SC-4 (bounded). The three landmines are
in the must_haves: inventory restore MUST run before the DELETE (deplete_for_order_item
reads the row by id and silently no-ops if it's gone), the audit call MUST be `PERFORM`
not `SELECT` (CI grep), and the deletions reports MUST read `audit_logs` (plural) not the
legacy `audit_log` (singular) — the latter silently returns zero rows forever.
Depends on Plan 01 (order_item.remove registered so the audit-actions.test.ts grep gate is
satisfiable). Output: 2 migration files. NOT pushed here — Plan 05 owns the push.
</objective>
