<objective>

Purpose: today `seatParty` only stamps `table_id`/`status`/`seated_at` on the waitlist entry, leaving staff to open a tab and start the timer as two disconnected manual steps on `/pool-tables`.

Output: one new mutation hook, one rewired call site, and unit coverage of all three table-type branches.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `SeatPartySheet` (manager-facing UI) → `seat_waitlist_party_and_start_session` RPC | Client-chosen `entryId`/`tableId` plus client-sourced `staffId`/`shiftId`/`cajaSessionId` cross into a `SECURITY DEFINER` function that writes to four tables. |
| Zustand stores → RPC identity parameters | `currentStaff.id` and `currentShift.id` come from client state and are written verbatim into `tabs.staff_id`/`tabs.shift_id`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-0711-01 | Spoofing | `p_staff_id` / `p_shift_id` sourced from client state, attributing a tab to an arbitrary profile | medium | mitigate | The RPC's first statement re-asserts the bypassed `waitlist_entries` manager+ RLS policy via `get_user_role()` (07-09, T-0709-02), so only a manager/admin session can invoke it at all. `tabs.staff_id` and `shift_id` carry FK constraints to `profiles`/`shifts`, so a fabricated id aborts the whole transaction rather than writing a bogus attribution. Identical to the trust model `useMutationOpenTab` has operated under since Phase 1 — this plan does not widen it. |
| T-0711-02 | Elevation of Privilege | A bartender reaching the seat action | high | mitigate | Two independent layers: the `/waitlist` page is gated client-side by `manage_waitlist` (manager+, confirmed in `src/shared/lib/rbac.ts` — no new RBAC action needed), and the RPC re-checks `get_user_role()` server-side. Neither layer alone is trusted. |
| T-0711-03 | Tampering | Stale client cache offering an already-occupied table in the picker | medium | mitigate | The branch and the occupancy check are both server-side under a `FOR UPDATE` row lock, so a stale `['resources']` cache produces a clean `POOL_TABLE_OCCUPIED` error Result rather than a double-seat. Deliberately NOT solved by client-side filtering (D-07 keeps the picker query as-is). |
| T-0711-04 | Repudiation | Auto-created tab indistinguishable from a manual one in the tab list | low | accept | D-01's `"{name} ({party_size})"` naming is itself the marker, and `tabs.staff_id` records the acting manager. Same disposition as T-0709-04; no decision asked for audit rows. |
| T-0711-05 | Information Disclosure | Party name rendered into a tab name visible on shared POS screens and printed tickets | low | accept | Directly mandated by D-01, and the party name is already displayed openly on the `/waitlist` board. No new exposure. |
| T-0711-SC | Tampering | npm/pip/cargo installs | n/a | n/a | No package installs in this plan. No `## Package Legitimacy Audit` required. |
</threat_model>
